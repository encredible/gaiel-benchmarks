# 작업 기록 (2026-08-19)

Gaiel 모델군을 감사하고 벤치마크 기반을 세운 하루의 기록. **틀렸던 판단도 그대로 남긴다.**

## 왜 시작했나

RunPod 에서 72B 다음 체급을 파인튜닝하려던 것이 출발점이었다. 그런데 기존 모델의 실태를
확인하는 과정에서 **공개된 모델 상당수가 비어 있거나 베이스보다 나쁘다**는 것이 드러나,
새 학습보다 감사가 먼저가 됐다.

## 시간순 요약

**1. 청사진 실사 — 코드가 시뮬레이션이었다**
`gaiel_fine_tuning_engine.py` 의 학습 루프는 `random.uniform` 으로 loss 를 만들어내고 0.1초 자는
것이 전부였다. `gaiel_llm_distiller.py` 의 "가중치 합성" 도 딕셔너리 생성기였고,
아키텍처 파일의 `composite_score 99.88` 은 측정값이 아니라 하드코딩된 목표치였다.
**이식할 학습 기법은 없었다.**

**2. HF 레포 감사**
24개 중 문제가 15개였다. 가중치 0바이트인 공개 레포 7개, 한국어판과 LFS 해시가 전부 같은
중복 1개, 그리고 이후 회귀로 확인된 6개.

**3. 로컬 MLX 측정 시도 → 포기**
16GB M4 로는 1.5B 하나에 30분이 걸렸고, 세션 종료와 함께 작업이 반복적으로 죽었다.
`launchd` 로 분리해 해결했으나 32B 이상은 램 부족으로 애초에 불가능했다. RunPod 로 전환했다.

**4. RunPod 환경 구축 — 네 겹의 실패**
`dockerArgs` 충돌, CUDA 버전 불일치, python 인터프리터 불일치, transformers API 제거.
자세한 내용은 [RUNPOD.md](RUNPOD.md).

**5. MLX LoRA → PEFT 변환**
1.5B/7B 의 "어댑터" 는 PEFT 가 아니라 MLX 학습 체크포인트여서 CUDA 에서 로드되지 않았다.
수식 대응(`A = lora_aᵀ`, `B = lora_bᵀ`, `alpha = scale × r`)을 맞춰 변환했고,
**ΔW 최대 절대오차 0.000e+00** 로 등가를 확인했다. 도구: [`tools/mlx2peft.py`](../tools/mlx2peft.py)

**6. 측정 → 네 체급 전부 회귀**

| 체급 | 한국어 Δ | 코딩 Δ |
|---|---|---|
| 1.5B | −2.7 | **−39.0** |
| 7B | −6.9 | −6.7 |
| 8B | −5.5 | **−50.0** |
| 32B | −6.8 | −9.1 |

**7. 정리**
회귀가 증명된 6개 레포 삭제. 근거 없는 것(측정 안 된 코딩 튜닝본)은 보존.
삭제 전 학습 설정과 측정치를 [ARCHIVE.md](ARCHIVE.md) 에 남겼다.

## 틀렸던 판단들

기록의 핵심은 여기다.

**① "`scale 20` 이 회귀의 원인이다" — 부분적으로만 맞았다**
1.5B/7B 는 alpha/r = 20 (통상값의 10배) 이었고 이것이 1.5B 코딩 −39pt 같은 극단값을 설명한다.
그러나 **alpha/r = 2 로 정상인 32B 도 −6.8/−9.1 로 회귀했다.** 하이퍼파라미터는 원인이 아니었다.
남은 공통 원인은 학습 데이터다.

**② "7B 는 LoRA 가 8개 레이어에만 걸려서 피해가 작을 것" — 반만 맞았다**
코딩은 맞았고(−6.7 vs 1.5B 의 −39.0), 한국어는 틀렸다(−6.9 vs −2.7). 7B 가 오히려 컸다.

**③ "Coder-14B 가 32B 를 이긴다" — 틀렸다**
우리 측정으로는 14B(85.9) > 32B(82.2) 였고 그렇게 보고했다. 그러나 그 우위는 전적으로
`humaneval_plus` 와 `mbpp_plus` 에서 나왔는데, 공개값과 대조하니 **그 둘이 가장 크게 어긋나는
지표**였다 (−8~−13pt, +6~+15pt). 공식값 기준으로는 32B 가 모든 지표에서 14B 이상이다.
대조 내역: [REFERENCE.md](REFERENCE.md)

**④ "MBPP+ 0.0 은 하네스 결함" — 절반은 내 설정 실수였다**
`mbpp_plus_instruct` 는 실제로 `extract_code` 필터 결함이 맞다. 그러나 `humaneval_plus` 가 0.0 이
나온 것은 **비-instruct 태스크에 `--apply_chat_template` 를 건 내 잘못**이었다.

**⑤ Δ 계산 버그 — 회귀를 개선으로 뒤집었다**
코딩 태스크를 1개에서 3개로 늘리자, 태스크가 1개뿐인 Gaiel 과 3개인 베이스의 **평균끼리 빼는**
상황이 됐다. `gaiel-32b` 가 **"+5.2 개선"** 으로 표시됐다. 실제로는 −9.1 회귀다.
Δ 를 양쪽 공통 태스크로만 계산하도록 고쳤다.

## 확립한 규칙

1. **베이스 점수를 먼저 찍는다.** 회귀는 처음부터 있었지만 비교 대상이 없어 몇 달간 발견되지 않았다.
2. **같은 하네스·같은 정밀도로 잰 것만 같은 표에 올린다.** 공개 수치는 별도 문서에 출처와 함께 둔다.
3. **새 지표는 공개값이 있는 모델로 보정한 뒤 쓴다.** 검증 안 된 지표로 모델 선택 결론을 내지 않는다.
4. **Δ 는 양쪽 공통 과제에서만 계산한다.**
5. **삭제하더라도 학습 설정·측정치·사유를 남긴다.** 모델을 지우면 근거도 사라진다.

## 다음 학습에 반영할 것

- `alpha/r ≤ 2`, rank 8~16
- **replay 20~30% 필수** — 한국어만 먹여 코딩이 −39~−50pt 지워졌다
- 학습 중 **HumanEval 하락 ≤ 2pt** 를 조기 종료 조건으로 건다
- 코딩 베이스는 Coder 계열 — 전 체급에서 범용 대비 우위 (1.5B +9.7, 7B +11.7)

## 남은 일

- 코딩 튜닝 자체는 아직 시작하지 못했다 (16칸 매트릭스의 코딩 열이 비어 있음)
- 한국어 코딩 합성 데이터 (R1) 미완
- `Gaiel-1.5B-Coding-Tuned-MLX` 미측정 (MLX 전용)
- 72B 미검증 (32B 와 동일 레시피라 회귀 추정, 측정 생략)
- 110B 코딩 어댑터 미평가 (Qwen1.5 구세대)
